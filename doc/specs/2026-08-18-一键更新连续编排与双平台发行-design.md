# 一键更新连续编排与双平台发行设计（2026-08-18）

## 目标

用户在应用内保存一次简历并点击一次“一键更新”后，软件按招聘方向和公司顺序逐站处理。每当官网需要登录、验证码或人工核对时暂停；用户点击顶部“完成”后，软件自动重试当前目标或进入下一目标，直到队列结束。整个过程中不得自动点击保存、提交简历、申请职位或投递按钮。

最终成品继续使用 Electron 共用一套 macOS/Windows 业务代码，并由 electron-builder 分别产出 macOS DMG/ZIP 和 Windows NSIS 安装包。

## 方案选择

### 采用：由渲染层驱动下一阶段，主进程维护唯一游标

- 主进程 `ResumeSyncSession` 继续作为队列进度的事实源。
- 渲染层抽出一个统一的“执行同步阶段并吸收结果”函数，按钮首启和顶部栏完成事件都调用它。
- 登录暂停完成后，主进程游标仍指向当前目标；渲染层立即重试当前目标。
- 核对或人工维护完成后，主进程游标指向下一目标；渲染层立即打开下一目标。
- 每次仍只允许一个内嵌工作区，防止两个招聘站互相覆盖。

该方案复用现有 IPC、适配器和会话边界，改动范围最小，也能使现有 Electron 端到端测试直接验证用户行为。

### 不采用：主进程后台递归执行

主进程可以在 `workspace:finish` 内直接再次调用同步编排器，但这会让 IPC 生命周期跨越多个页面暂停点，错误提示、界面状态和任务日志更难同步。

### 不采用：保持每站再次点击“一键更新”

这种方式改动最少，但不符合“一键更新”的产品语义，也与现有端到端测试期望冲突。

## 连续同步状态流

1. 用户点击“一键更新”，渲染层先保存当前简历。
2. 渲染层调用 `fillResumeToAll(startCompanyId)`。
3. 适配器出现以下结果之一：
   - `login-required`：保留当前官网与顶部栏。
   - `review-required`：保留已填写页面供用户核对。
   - `manual-required`：保留页面供用户手动维护。
   - `failed`：记录失败并由编排器继续，直至下一暂停点或队列结束。
4. 用户点击顶部“完成”：
   - 登录暂停：自动重试当前目标，以便登录成功后继续填表。
   - 核对/手动维护暂停：自动进入下一招聘方向或下一公司。
5. 新目标再次需要用户时继续暂停；不需要用户时自动向后推进。
6. 队列结束后展示已核验、需人工和失败的平台汇总，不把仅打开网页计为更新成功。

取消按钮始终停止自动推进，并把游标保留在当前目标，等待用户以后重试。

## 安全边界

- 自动化只做导航、字段识别、字段写入和写后回读。
- 密码、验证码、提交、申请、投递、支付和协议确认控件永久禁填禁点。
- “完成核对”只表示关闭当前工作区并推进队列，不代表软件替用户点击官网保存。
- 腾讯校招等“提交简历即投递”的页面必须继续显示风险提示。
- BOSS 直聘保持协议限制，不进入自动更新队列。
- 真实更新使用用户现有本机登录会话；不得上传简历或登录态到第三方服务。

## 错误处理

- 顶部“完成”在自动推进期间临时防重复触发。
- 如果新阶段返回 `workspace-active`，界面保留当前游标并提示用户处理现有页面，不创建第二个工作区。
- 登录并未完成时，重试仍会回到 `login-required`，不会跳过当前公司。
- 单个平台结构变化或网络失败写入任务日志，编排器继续寻找下一可处理目标。
- 应用退出或用户取消后不在后台继续导航。

## 验证策略

### 自动化

1. 保留并先运行当前失败的 `test/ui-resume-sync-all.cjs`，证明腾讯社招完成后会自动打开腾讯校招。
2. 增加登录暂停后自动重试当前目标的回归断言。
3. 增加取消后不自动推进的回归断言。
4. 运行全部 Node 单元/集成测试、静态检查和全部 Electron UI 回归。
5. 运行介绍页桌面与移动端冒烟测试。

### 真实站点

按腾讯社招、腾讯校招、字节社招、阿里社招的顺序进行：

1. 使用本机已有登录态打开简历页。
2. 记录自动识别、成功回读和需要人工处理的字段。
3. 人工核对页面内容；只在确认是“保存个人简历”而非投递时保存。
4. 重新打开简历页并回读保存结果。
5. 将实测日期、字段数、失败组件和页面风险写入 `doc/progress/`。

百度、小米、京东、美团当前仍是人工维护入口，不得因为被队列打开就宣传为自动更新完成。

## 跨平台发行

### 框架

继续使用 Electron。现有主进程、渲染层、`path` 路径处理和 electron-builder 配置已经同时支持 macOS 与 Windows，无需迁移到另一套框架。

### 构建产物

- macOS：在 macOS runner 生成 Apple Silicon DMG、ZIP 和 SHA256；未取得 Developer ID 前明确标注未签名。
- Windows：在 Windows runner 生成 x64 NSIS `Setup.exe` 和 SHA256。
- 两个平台都从同一个 Git 标签构建，应用版本、介绍页版本和 Release 标签必须一致。

### 构建方式

新增 GitHub Actions 发行工作流，使用 macOS 与 Windows 矩阵分别运行测试和打包。构建产物先作为 Actions artifact 留存；只有版本标签触发时才上传到同一个 GitHub Release。这样每个平台都在自己的原生系统构建，避免从 Mac 交叉生成未经启动验证的 Windows 安装包。

### 发行门槛

- 全部自动化测试通过。
- macOS 应用在本机完成启动、简历保存和内嵌工作区回归。
- Windows 安装包至少在 Windows runner 完成安装/启动冒烟测试；若没有真实 Windows 图形环境验证，Release 必须标为内测。
- Release 同时包含 DMG、macOS ZIP、Windows Setup、各自 SHA256 和安装说明。
- GitHub `main`、标签、Release 与介绍页不再出现版本错位。

## 不在本轮承诺

- 不自动投递职位。
- 不绕过验证码或招聘平台风控。
- 不把仍为 `manual` 的平台升级为 `verified`。
- 不承诺未签名 macOS 包已通过 Apple 公证。
- 不承诺在没有真实 Windows 环境验证时达到正式稳定版质量。
