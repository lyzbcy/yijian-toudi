# 一键投递完整落地设计

> 状态：已批准执行
> 日期：2026-07-25
> 授权说明：用户要求三个子项目依次全部完成，并明确要求不中途等待一般产品选择。

## 1. 现状审计

项目已经具备可运行的 Electron 桌面应用、GitHub Pages 介绍页、macOS 安装包、本机 Agent API、QQ 邮箱同步、统一简历、购物车，以及腾讯、百度、字节跳动、小米、京东、美团的岗位抓取器。基础测试 4 项、项目静态检查、桌面冒烟测试和介绍页桌面/移动端冒烟测试均通过。

当前主要缺口不是界面数量，而是真实浏览器闭环与发布质量：

1. 腾讯简历填写器和投递器创建的是未挂载到窗口的 `WebContentsView`，用户看不到结果；执行器随后销毁视图，无法完成最终确认。
2. 投递购物车把“已打开表单”等中间状态也计入成功，并且无论失败与否都会清空购物车。
3. 简历填写依赖模糊关键词匹配，没有可复核的字段差异、命中报告和人工确认面板。
4. Agent 命令没有幂等键与操作审计，重复请求可能重复启动外部动作。
5. 线上最新 Release 仍是 `v0.1.0`，说明文字仍称岗位为演示数据，与当前六家真实抓取实现不一致。
6. 更多公司目前只有入口或调研记录，没有统一的能力声明、健康检查与安全降级。

## 2. 路径选择

### 方案 A：横向铺开

先为更多公司增加岗位抓取器，再统一补投递。优点是公司数量增长快；缺点是会继续累积“看起来支持、实际不能完整使用”的半成品。

### 方案 B：纵向闭环（采用）

先把腾讯的登录、简历预览、自动填写、投递确认、状态记录做成完整闭环；再完善内测发布；最后按统一契约扩展公司。优点是最早得到一个可验证的真实样板，后续每家公司都能复用相同边界；缺点是第一家公司需要更严谨的基础设施。

### 方案 C：通用 AI 视觉操作

把网页内容交给模型实时识别并操作。优点是适应改版快；缺点是成本、稳定性和安全性都不适合日常全量任务。仅在固定选择器健康检查失败时作为诊断辅助，不作为默认执行路径。

## 3. 总体架构

采用本地优先的“固定适配器 + 可见浏览器工作区 + 人工确认门”：

```text
桌面界面 / 本机 Agent API
        ↓
动作编排器（幂等键、队列、审计、状态机）
        ↓
公司能力适配器
  ├─ listJobs
  ├─ inspectResume
  ├─ planResumePatch
  ├─ fillResume
  ├─ prepareApplication
  └─ inspectApplicationStatus
        ↓
可见浏览器工作区（每家公司独立持久化 session）
        ↓
招聘官网
        ↓
最终保存/最终投递前由用户确认
```

Kimi WebBridge 的本地桥接思路只作为架构参考：动作在本机执行并复用用户真实登录态。本项目不复制其浏览器扩展，而是在 Electron 内提供受限的本机桥接层；固定脚本负责常规任务，异常页面才暂停并交给用户。

## 4. 阶段一：腾讯真实闭环

### 4.1 可见浏览器工作区

`login-manager` 升级为通用浏览器工作区管理器。登录、简历填写和岗位投递都复用同一个挂载到主窗口的可见 `WebContentsView`，并使用 `persist:tencent` 会话。

工作区有四种模式：

- `login`：用户完成登录或验证码。
- `resume-review`：软件填写字段后，用户核对并点击官网保存。
- `application-review`：软件准备好投递表单，用户核对并点击官网最终提交。
- `browse`：仅浏览招聘官网。

关闭工作区前刷新 cookie 与存储。执行器不再自行销毁视图；只由用户点击“完成”或主流程明确取消后关闭。

### 4.2 简历差异与填写报告

简历同步分成三步：

1. 读取可识别的远端表单字段和当前值。
2. 生成本地值、远端值、计划动作和风险提示组成的差异清单。
3. 用户点击“开始填写”后写入页面，返回逐字段命中报告。

默认不触发官网保存按钮。没有稳定映射的字段标记为“需手动填写”，不使用近似字段静默覆盖。教育、工作与项目经历按条目处理，不把多条经历压入一个输入框。

### 4.3 投递状态机

每个购物车岗位独立记录：

- `queued`：等待处理。
- `login-required`：需要登录或验证码。
- `review-required`：已打开表单，等待用户确认。
- `submitted`：页面明确显示提交成功。
- `manual-required`：页面结构未知，需要用户手动完成。
- `failed`：网络、页面或适配器错误。

只有 `submitted` 才进入“已投递”。其他岗位保留在购物车并显示下一步，不再把“表单已打开”计为投递成功。

### 4.4 测试边界

自动测试覆盖状态机、购物车保留规则、字段映射、幂等请求和页面探针。真实账号端到端测试只运行到最终保存/提交前；验证码与最终外部写入始终由用户接管。

## 5. 阶段二：可发布内测版

### 5.1 首次使用与隐私

首次向导明确说明：

- 简历、邮箱授权码和招聘网站登录态保存在本机。
- 邮箱授权码由系统安全存储加密。
- Agent API 只监听 `127.0.0.1` 并需要 Token。
- 最终投递和简历保存由用户确认。
- 未签名 macOS 应用需要使用随包安装脚本授权。

增加本地数据备份与恢复。恢复前验证版本和结构，并自动保留恢复前备份。

### 5.2 更新与发布

版本升级为新的内测版本。应用启动时检查 GitHub Release；发现新版本后展示版本号、发布说明和下载入口。介绍页下载按钮指向最新 Release，并同步更新真实能力说明。

发布物包括：

- macOS Apple Silicon ZIP。
- 未签名安装授权脚本。
- 安装说明。
- SHA256。
- 版本变更说明。

DMG 只有在本机打包验证通过后发布。GitHub Pages 的 `PAGE_V` 与 `version.json` 同步递增，避免用户看到旧缓存。

### 5.3 Agent API

外部写操作要求 `Idempotency-Key`，同一键重复请求返回第一次结果。所有命令写入本地审计记录，包含时间、动作、来源、目标和结果，不记录 Token、邮箱授权码或网页凭证。

读接口保留现有能力；写接口返回任务 ID，由 `/v1/tasks` 查询进度。涉及可见浏览器或人工确认的命令返回 `review-required`，不伪装成已完成。

## 6. 阶段三：逐家公司扩展

### 6.1 能力声明

每家公司显式声明以下能力：

```js
{
  jobs: 'verified' | 'degraded' | 'unsupported',
  login: 'verified' | 'manual' | 'unsupported',
  resume: 'verified' | 'manual' | 'unsupported',
  apply: 'verified' | 'manual' | 'unsupported',
  status: 'verified' | 'manual' | 'unsupported',
  lastVerifiedAt: 'YYYY-MM-DD'
}
```

界面和官网只展示真实能力，不再用一个“已支持”概括不同层级。

### 6.2 扩展顺序

按已有证据和复用成本依次推进：

1. 腾讯：完整样板。
2. 字节跳动与小米：共用飞书 ATS 结构。
3. 京东与美团：已有公开岗位接口。
4. 百度：已有 SSR 岗位数据。
5. 华为与阿里：已知公开入口，补全参数和页面探针。
6. 网易、拼多多、米哈游：需要登录态或风控页面，默认以可见浏览器和人工接管方式降级。

每家公司只有在岗位抓取、登录恢复、简历字段映射、失败可见、最终确认和真实账号回归全部有证据时，才把对应能力标为 `verified`。

### 6.3 改版检测

每个固定适配器维护页面/API 指纹和最后验证日期。指纹不匹配时：

1. 停止自动写入。
2. 把能力降级为 `degraded`。
3. 保留页面摘要、URL 与错误类型到脱敏诊断记录。
4. 提示用户手动继续，不尝试绕过验证码或风控。

## 7. 数据与安全

- 所有账号凭证、登录 cookie、邮箱授权码和简历正文默认只保存在本机。
- 日志和导出默认脱敏 Token、授权码、cookie、手机号和身份证号。
- Agent API 不绑定公网地址，不开放任意 URL 导航，不执行任意 JavaScript。
- 最终提交、保存、发送邮件等外部写入动作必须通过可见页面由用户确认。
- 对失效岗位、未知页面和验证码使用明确状态，不自动重试可能产生重复投递的动作。

## 8. 错误处理

- 网络失败：保留旧数据，记录本次失败，不用空结果覆盖成功缓存。
- 登录失效：切换到 `login-required`，打开可见登录页。
- 页面改版：停止自动填写，生成诊断信息并降级。
- 部分字段失败：保留成功字段的报告，失败字段转为手动清单。
- 用户取消：任务标为 `cancelled`，购物车与简历计划不丢失。
- 重复 Agent 命令：按幂等键返回原任务，不再次执行。

## 9. 验收标准

### 阶段一

- 腾讯登录态重启后仍可复用。
- 简历填写结果在应用内可见，逐字段报告可核对，软件不点击最终保存。
- 投递表单在应用内可见，软件不点击最终提交。
- 只有页面明确成功的岗位才移入“已投递”；失败或待确认岗位保留。

### 阶段二

- 单元、静态、桌面与介绍页测试通过。
- 首次向导、隐私说明、备份恢复和更新检查可操作。
- Agent 写命令具备幂等与审计。
- 新版本 macOS 发布物、校验值、安装说明和介绍页下载链路一致。

### 阶段三

- 公司能力矩阵与代码事实一致。
- 已验证抓取器不会因单家公司失败阻断其他公司。
- 未验证的简历与投递能力明确降级为手动，不出现虚假成功。
- 每家公司都有选择器/API 证据、失败策略和最后验证日期记录。

## 10. 连续执行约定

执行过程中不为普通界面文案、文件拆分或技术细节暂停。遇到真实账号登录、验证码、最终投递、发布授权之外的阻碍时，优先采用安全降级并继续下一项；所有无法在无凭证环境中完成的真实验证会记录为明确的人工验收项，不会冒充完成。
