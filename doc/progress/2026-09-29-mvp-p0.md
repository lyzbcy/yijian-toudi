## 审计依据与结论

- 对照工作树 v0.5.2、Git 中 v0.5.0 提交 `46a9082` 的批量脚本、交接 prompt 与 `scripts/boss-batch-monitor.cjs`。
- 仓库历史脚本也有 3–6 秒搜索等待和 25–45 秒投递等待。还没有找到能与用户所说“Z Code 每天成功 100 多份”一一对应的脚本及运行记录，不能宣称已找出两者全部差异，或已证明 403 的唯一原因。
- 本地新增四个反例在修改前全部失败：详情等待期间停止后仍操作；搜索等待结束仍导航；发送点击抛错未设结果不明；停止后在途回执仍点击“留在此页”。这是可复现的软件缺陷，不依赖任何真实网站请求。
- 旧主进程在 stop 请求时就把 running 置 false，但异步任务尚在运行；新批可覆盖全局 runner，旧回调可能操作新任务。停止状态仅在内存，重启后会丢失原因与待确认发送。

## v0.5.3 本轮变更

1. Runner 所有导航/发送前检查停止状态；等待可被停止唤醒。在途回执已返回时仍如实计数，不再额外点击页面。
2. `BossBatchController` 统一 IPC/HTTP 生命周期。启动在第一个 await 前占锁；停止中保持 running=true，直到异步任务真正结束。通知故障不控制核心事务。
3. `state.bossBatchRun` 记录 runId、账号、phase、目标、pending、applied、previewed、停止原因和复核状态。`bossBatchHistory` 保留最近 50 批。
4. 每次发送前先提交 pending；回执确认后，成功记录、公司去重与 pending 清空在同一次 JsonStore 写入中完成。写盘失败停止；未知发送不计成功。
5. 重启发现未结束任务，或安全验证/403/发送未知/落盘失败时阻断新批次。时间到达本身不会自动解除。
6. UI 显示“停止中”与“核对上次异常”，禁止未复核直接启动。`POST /v1/boss/batch/resolve` 必须带当前 runId 与明确 action；过期请求不生效。未知公司加入 heldCompanies，保持跳过但不增加成功计数。复核仅解锁，不触发投递。
7. 目标数限定正整数，dryRun 限定布尔值；客户 50、自用 120 上限与账号成功记录隔离保留。
