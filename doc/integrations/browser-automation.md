# 浏览器自动化与验证码策略

## 目标

应用通过本地桥接层控制用户电脑上的 Chrome/Edge，与 Kimi WebBridge 的核心思路一致：Agent 把动作交给本地服务，浏览器在本机完成导航、点击、读取与填写，登录态不上传。

当前 MVP 已实现“用独立 profile 打开公司招聘官网并保留登录态”，但未实现逐站抓取和填表。

## 适配器契约（下一阶段）

每家公司单独维护：

1. `detectLogin(page)`：判断是否需要登录。
2. `listJobs(page, filters)`：分页读取岗位。
3. `normalizeJob(raw)`：清洗成统一字段。
4. `readProfile(page)`：读取平台已有简历。
5. `diffProfile(local, remote)`：只生成差异。
6. `fillProfile(page, patch)`：填表但默认不做最终提交。
7. `apply(page, job)`：最终提交前必须等待用户确认。

## 验证码经验

参考“知识库 AI 开发第二期”的 2026-06-17 结论：

- 旧项目曾因 `HeadlessChrome` UA 被腾讯风控判为环境异常；修复浏览器环境后链路才通过。
- 缓存或复用旧浏览器会话前必须校验会话状态，不能默认安全复用。
- 纯视觉识别对不同拼图并不稳定，不应成为通用承诺。

本项目采用更保守的产品策略：

- 默认用真实有界面的系统浏览器；
- 登录、验证码和异常风控页面出现时暂停并提示用户接管；
- 不在未获得站点授权与稳定证据前内置“绕过风控”的行为；
- 每个适配器都要记录最后实测日期，网站改版后自动降级为“需要维护”。

## Token 节约

招聘站点稳定后，优先使用经过回归测试的固定选择器与清洗脚本；只有结构检测失败时才把页面摘要交给 Agent 分析。这样将日常全量更新的模型消耗降到最低。
